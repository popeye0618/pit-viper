# 테스트 스타일

> **이 파일이 규칙이다.** pit-viper 는 테스트를 쓰기 전에 이 파일을 읽고, 여기 적힌 대로만 쓴다.
> 마음대로 고쳐도 된다 — 프로젝트 관례가 곧 이 파일이다.
> 지우면 다음 실행 때 이 기본값으로 다시 만들어진다.

## 명명

- 테스트 클래스는 `<대상클래스>Test`
- 테스트 메서드 이름은 **영어**로, 짧고 의미가 분명하게 (`allowsOnlyBelowMax`, `rejectsNegativeMax`)
  - 문장을 통째로 옮기지 않는다. 서술은 `@DisplayName` 이 한다
- `@DisplayName` 은 **한국어 서술문**으로 "무엇을 보장하는가"를 적는다
  - `"상한 미만이면 허용하고 상한에 닿으면 막는다"`
  - 메서드 이름을 한글로 옮긴 것(`"허용한다"`)은 쓸모가 없다
- 클래스에도 `@DisplayName` 을 붙인다

## 구조

- 관련된 케이스는 `@Nested` 로 묶는다 (구현별, 상태별, 메서드별)
- `@Nested` 클래스에도 `@DisplayName` 을 붙인다
- given / when / then 사이에 빈 줄 하나
- 공용 픽스처는 필드로, 케이스마다 다른 값은 지역 변수로
- 상수는 프로덕션 상수를 그대로 참조한다 (`FrameLimit.MAX` 처럼) — 숫자를 베껴 쓰면 상수가 바뀔 때 조용히 어긋난다

## 단언

- AssertJ — `assertThat`, `assertThatThrownBy`
- **정확한 값으로 단언한다.** `isPositive()` · `isNotNull()` · `isNotZero()` 는 쓰지 않는다
  - 계산이 틀려도 통과하기 때문에 생존 뮤턴트의 주범이다
- 예외는 타입까지 단언한다. 메시지까지 볼지는 그 메시지가 계약인지에 달렸다
- 한 테스트에 단언이 여럿이어도 좋다 — **같은 규칙의 여러 지점**이면 묶는 게 읽기 좋다
  (경계 삼점 세트, 열거형 전수 확인)

## 하지 않는 것

- 프로덕션 코드 수정. 테스트를 통과시키려 `src/main` 을 고치는 것은 실패다
- 기존 테스트 삭제·약화
- `@SpringBootTest` 로 순수 로직을 테스트하는 것 — 단위로 충분하면 단위로

## 프로젝트별 추가 규칙

<!-- 이 프로젝트만의 관례를 여기 적는다. 위 규칙과 충돌하면 이쪽이 이긴다. -->

- **`src/test` 는 `src/main` 의 패키지 구조를 그대로 따라간다.**
- 기존 테스트 일부는 이 파일보다 먼저 쓰여서 **메서드 이름이 한국어**다
  (`같은_금액은_더_크지_않다()`). 굳이 옮기지 않되, **새 테스트는 위 규칙을 따른다.**
- 스킬 스크립트의 파이썬 테스트(`.claude/skills/pit-viper/tests/`)는 이 규칙 밖이다 —
  `unittest` 관례를 따르고 메서드 이름은 한국어로 쓴다.
